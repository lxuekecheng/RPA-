# 测试与发布

每次代码改动遵循：分支修改 → 本地测试及适用的真实环境验收 → PR 自动测试 → 合并 → `main` 完整复测 → 自动发布到 GitHub Releases。

## 自动测试

本地运行 `npm.cmd test`，需要 Node.js 22 及以上和 Chrome。测试会启动无界面 Chrome、使用虚构数据及本机模拟页面，不会操作真实 ITSM 合同。

`.github/workflows/ci.yml` 在向 `main` push、面向 `main` 的 PR 和手动触发时运行，在 Windows 上分别使用 Node.js 22、24：

1. 从 `package-lock.json` 安装依赖。
2. 确保 Chrome 可用。
3. 运行完整的 `npm test`，包括浏览器测试；任何一步失败都使该检查失败。测试入口还核对完整结果，零用例、跳过、待办、取消或缺少统计时均失败。

## GitHub 强制检查配置

CI 文件提交并至少成功运行一次后，在仓库 Settings → Branches 中为 `main` 添加保护规则：

- 开启 **Require a pull request before merging**。单人维护时不强制第二人批准，但仍通过 PR 检查变更。
- 开启 **Require status checks to pass before merging**，将以下两个检查列为必需：
  - `Windows tests (Node 22)`
  - `Windows tests (Node 24)`
- 开启 **Require branches to be up to date before merging**。
- 开启 **Do not allow bypassing the above settings**，让管理员也遵守检查。
- 保持不允许强制推送和删除 `main`。

检查必须来自 GitHub Actions，并与当前提交匹配。只有 CI 文件而未启用上述仓库设置，无法强制阻止未测试改动进入 `main`。

## 发布要求

自动测试成功只代表已执行用例通过。涉及 ITSM 页面定位、联动或保存流程的变更，需要在合并前于目标环境核对相应行为，并在 PR 中说明验收范围和结果。

`main` 的两组测试成功后，`release` 任务自动生成 ZIP、SHA-256 文件和 JSON 提交记录，并发布 GitHub Release。PR 和其他分支只测试。手动重跑流水线时也必须选择 `main`，完整测试通过后才能补发。

发布标签为 `v<package.json版本>-<提交SHA前12位>`，每次提交独立对应一个版本。ZIP 通过 `git archive` 从该次测试的准确提交生成，包含程序、测试、发布脚本和公开说明；本机配置、预算数据、执行历史、浏览器会话和依赖目录不进入发布包。

附件全部上传并校验成功后，草稿才转为正式 Release。重跑相同提交会复用原标签；已公开的下载文件不覆盖。发布页和 JSON 记录完整提交 SHA、CI 链接及 ZIP 校验值。

下载包用于 Windows 本机运行。解压后双击“启动工具.cmd”；首次启动会安装锁定依赖。升级时保留原有 `.local/` 配置、会话与执行历史。
